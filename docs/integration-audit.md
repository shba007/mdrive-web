# Integration audit: MDrive Web, MDrive backend, MMedia backend

Date: 2026-11-14. Read-only review of the three repos by code reading; nothing was run end to end and no R2 or Notion access was used.

```
MDrive Web (code-drive-web)
  -> MDrive backend (code-drive, Nitro, :3004)   R2: presigned URLs + cache, Notion: all records
       -> MMedia (code-media, Motia/III, :3111)  R2: read and write, Notion: (expected)
```

Flow today, as coded: web asks drive for presigned PUT URLs (`POST /api/media/uploads`, keys `upload/<org>/<project>/<name>`), the browser uploads straight to R2, an R2 event notification goes through the Cloudflare worker (`code-media/worker/r2-event.js`) to `mmedia POST /webhook/media/uploads`, mmedia extracts metadata, copies the file to `processed/...`, and reports progress to `drive PUT /webhook/uploads/status`, which writes Notion and updates the batch the web polls.

## Verdict

Web and MDrive backend are in sync (Cycle 7). **The MDrive backend and MMedia are not in sync: the upload pipeline cannot complete today.** Items 1 to 6 each break it on their own.

## Blockers (upload pipeline)

Drive's middleware protects `/webhook/*`, so every callback is 401. | 2   | drive -> mmedia    | Drive calls `POST {mediaUrl}/media/transform` (`server/routes/media/[kind]/[...rest].ts`) with no `x-api-key`; mmedia requires it (401). Drive has no env var for an mmedia key.                                                                                                                                                                                                                                                                                                                                                                                                                       | drive (add env + header)                                                                                                                                                                          |
| 3   | drive <-> mmedia   | File names disagree. Drive names uploads `<kind>-<org:4 digits>-<project:4>-<media:4>-<version:3>` with no batch or upload id in the key. mmedia assumes `<name>-<batchId>-<uploadId>.<ext>` and takes the last two dash parts as ids, so it reads `0001`/`001` as batchId/uploadId and the batch in drive is never found. | 4   | mmedia -> drive    | `mediaId` in the callback is mmedia's new file name, but drive treats it as a Notion page id (`notion.pages.update({ page_id: mediaId })`). Notion rejects it, so the webhook answers 500.                                                                                                                                                                                                                                                                                                                                                                                                             | drive (look the page up by slug or create it) or mmedia (send no id)                                                                                                                              |
| 5   | mmedia -> drive    | Drive reads `metadata.format.width/height` to set Aspect ratio and Resolution; mmedia's `format` has no width or height (only `resolution: "<width>p"` and `aspectRatio`). Result: every file gets 16:9 and 4320p. mmedia also labels the width as "p".                                                                                                                                                                                                                                                                                                                                                | mmedia (send `width`/`height`) and drive (fall back to `aspectRatio`)                                                                                                                             |
| 6   | web, drive, mmedia | `url` on every media item is `{NITRO_MDRIVE_PUBLIC_MEDIA_URL}/media/image/...`, which in dev is mmedia `:3111`. mmedia has no `GET /media/image/*` route (only `POST /media/transform`, `GET /media/:id/metadata`), so thumbnails 404. The route that serves them is in drive (`/media/:kind/**`).                                                                                                                                                                                                                                                                                                     | drive config: point the public media URL at drive (or the CDN in front of it), not mmedia                                                                                                         |

## Decision: MDrive owns file names (2026-11-14)

Contract to implement in the other two repos (item 3, and the naming part of 4):

- Drive names every upload `<kind>-<org:4>-<project:4>-<media:4>-<version:3>.<ext>` and stores the key `upload/<org>/<project>/<name>.<ext>`. It already does this and already records the same filename on `uploads[]` in the batch.
- mmedia never renames or renumbers. It copies `upload/<org>/<project>/<name>.<ext>` to `processed/<org>/<project>/<name>.<ext>` unchanged, so drive's Notion `Slug` equals the processed file name and the download and thumbnail keys match.
- mmedia stops parsing batch and upload ids from the name. Its callback sends `filename` (the full drive name), `projectId`, `status`, `progressPercent`, `error`, `data.metadata`, and `mediaId: null`.
- Drive's `PUT /webhook/uploads/status` finds the batch by `filename` (unique per batch), finds or creates the Notion page by the indexes in the name (so a Notion page id is never taken from mmedia), and updates `uploads[]`. `batchId` and `uploadId` in the body become optional.
- Remove from mmedia: the 5-digit org regex, `getMediaKind`-based renumbering, and the `r2GetAllFiles` numbering scan.

## What is in sync

- Web <-> drive: `x-api-key` and `x-org-id` headers, all `/api/*` routes, review submit, media detail, file facts in lists, reject comment flow, 401/403 handling, dev proxy on `:3004`, container proxy for `/api` and `/media`.
- Upload batch shape (`batchId`, `uploads[]` with `status`, `progressPercent`, `mediaId`, `error`) is the same in drive and web, so once the webhook works the web needs no change.
- mmedia's own routes and `x-api-key` check, and the Cloudflare worker forwarding with the key, are consistent with each other.

## Missing per repo

**code-drive:** send `x-api-key` to mmedia and add its env var (2); fix the callback handling of `mediaId` and photo dimensions (4, 5); agree the file naming (3); set the public media URL to drive or the CDN (6); decide read-only vs presigned PUT (storage row); document the real env names.

**code-media:** send `x-api-key` on callbacks (1); parse the key drive actually produces and keep drive's name (3); send `width`, `height`, `exif`, correct `resolution` (5); remove or implement the Notion step; fix `.env.example` port; filter the R2 event rule (loop risk).

## Questions for you

1. Who owns the file name: drive (keep its `photo-0003-0008-0001-001`) or mmedia (renumbers)? Recommended: drive, mmedia keeps it.
2. Should drive really be read-only on the bucket? If yes, uploads must be presigned by mmedia, which is a larger change.
3. Does mmedia need Notion at all? Recommended: no, drive stays the only Notion writer.
4. Should the thumbnails be served by drive's `/media` route (needs a shared disk with mmedia or an R2 hand-off) or by mmedia directly?
